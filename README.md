# Engine Optimizer (tModLoader)

Мод для tModLoader 1.4.4.x: измеряет реальную стоимость кадра и подсистем движка,
убирает часть микрофризов и пишет диагностику на диск.

## Что нового в 0.8.6

Ревизия кода нашла три вещи — одна из них настоящий баг:

1. **Баг: хуки роста тайлов не ставились без CalamityFables.** В `TryInstall` ранний
   `return` при ненайденном моде-цели дыма выходил из метода до установки хуков
   `UpdateWorld_OvergroundTile`/`UpdateWorld_UndergroundTile`/`HandleTileGrowth`.
   Теперь секции независимы: нет CalamityFables — дым просто пропускается,
   тайловые хуки ставятся всегда.
2. **Предзагрузка мира на паузе в бою.** Пока активен boss-режим (включая 2-секундное
   linger-окно после боя), `WorldPreloader` не тратит свой бюджет — это до
   `PreloadBudgetMs` = 3 мс/кадр обратно кадру боя. После боя продолжается с места
   остановки.
3. **Сканирование боссов — реально один проход на тик.** Результат кешируется по
   `Main.GameUpdateCount`: автосейв и BossPerfMode делят один проход по NPC-таблице
   (в v0.8.4 это декларировалось, но вызовов всё равно было два).

## Что нового в 0.8.5

1. **Приоритет процесса `AboveNormal` в мире** (`BoostProcessPriority`, вкл. по умолчанию).
   Частоту турбобуста (до 3.1 ГГц) мод поменять не может — это территория ОС/BIOS, —
   но реальная причина «недобора» CPU часто не в частоте, а в вытеснении: браузер,
   Discord, индексация поиска отбирают кванты у игры. AboveNormal убирает это
   вытеснение: планировщик отдаёт ядра игре. Поднимаем только с Normal (кастомные
   приоритеты не трогаем), только в мире, после выхода — исходный. Текущий приоритет
   виден в `live.json` (`proc_priority`).
2. **Boss-режим шире: рост тайлов мира.** На время боя ранним выходом
   приостанавливаются `WorldGen.UpdateWorld_OvergroundTile` / `UpdateWorld_UndergroundTile`
   / `HandleTileGrowth` (~0.8 мс кадра по профилю): трава/лианы/кактусы не растут
   минуту боя — визуально незаметно. В мультиплеере не влияет (мир обновляет сервер).
   Сводка в оверлее теперь `on (smoke+fx+world)`, в `live.json` — `boss_perf_tile_hooks`.
3. Оверлей `boss perf` показывает, какие хуки реально стоят.

## Что нового в 0.8.4

Разбор «аномалии 213 снарядов» из старых трасс (общее число было видно, но не ЧЬИ
это снаряды):

1. **`projectile_top` в телеметрии.** Когда снарядов становится аномально много
   (≥100), в `live.json`, `timeline.csv` и `spikes.csv` пишется топ-3 типа с
   количеством и именем — для модовых снарядов точное `Мод:Класс`, для ванильных
   локализованное имя. Считается только в момент записи (не каждый кадр).
   Пример: `type 646 'CalamityMod:AshRain' x180; type 94 x31`.
2. **Подсветка в оверлее:** строка `dust / proj / npc` желтеет, когда снарядов
   больше 150 — сигнал посмотреть в `live.json`, кто их породил.
3. **Мелкие фиксы:** состояние боя не переносится между мирами (linger-таймер
   BossPerfMode сбрасывается на входе в мир); сканирование боссов unified —
   один проход по NPC-таблице на автосейв и BossPerfMode вместо двух.

## Что нового в 0.8.3

По итогам CPU-профилей главного потока в боях с боссами (модпак с CalamityFables):

1. **Режим босс-боёв (`BossPerfMode`, вкл. по умолчанию).** Профиль показал, что
   ~21% кадра (6.4 мс) съедал дым из CalamityFables —
   `CalamityFables.Particles.MergeBlendSmokeRenderTarget.DrawSmoke`.
   Теперь на этот метод ставится IL-хук с ранним выходом: пока рядом босс
   (радиус 125 тайлов), тело метода не выполняется вовсе. Дополнительно в бою
   принудительно выключаются `Main.UseHeatDistortion` и `Main.UseStormEffects`
   (тяжёлые шейдерные проходы, малозаметные в бою). Через 2 секунды после
   конца боя — с анти-миганием между фазами босса — всё возвращается как было.
   Если CalamityFables не загружен, хук просто не ставится; состояние видно
   в строке `boss perf` оверлея и в телеметрии (`boss_perf`, `boss_perf_smoke_hook`
   в `live.json`, колонка `boss_perf` в `timeline.csv`).
2. **Фикс F6.** Подсказка в углу оверлея показывала жёстко зашитую строку «F6» и
   врала после перепривязки клавиши — теперь берётся реальная привязка из профиля
   управления. Плюс переключение подтверждается сообщением в чате, чтобы нажатие
   не выглядело «не работающим» при скрытом оверлее/в меню.
3. **Меньше оверхеда измерений.** `PerfData.MsSince` вызывается десятки раз за кадр
   из каждого хука; деление на `Stopwatch.Frequency` заменено умножением на
   заранее посчитанный коэффициент.
4. Оверлей: новая строка `cursor` (время обновления аппаратного курсора) слева и
   `boss perf` (состояние режима босс-боёв) справа.

## Что мод делает и чего не делает

**Делает:**

1. **Честно считает FPS** — по числу реально отрисованных кадров за секунду
   (`fps_draw`), а не по сглаженному `1/dt`, который завышает при рваном кадре.
2. **Пишет диагностику на диск каждую секунду**, пока вы играете: `live.json`,
   `timeline.csv`, `spikes.csv` с причиной каждого кадра дольше 25 мс
   (`preload`, `save`, `gc`, `section`, `gpu`, `update`, `draw`, `other`).
   Файлы не нужно никуда отправлять — ответ уже в них.
3. **Убирает главные источники «стоп-кадров» в модпаке:** GC-паузы (`SustainedLowLatency`),
   ленивый пересчёт секций мира при ходьбе (предзагрузка на входе), автосейв во время боя
   с боссом (откладывается), запись телеметрии (фоновый поток).
4. **Параллелит только визуальные подсистемы**, которые к этому готовы: gore (по умолчанию),
   дождь (опционально, выключен). Геймплей — нет.

**Не делает и не будет (честно):**

- не переписывает движок Terraria — это мод на хуках, а не форк;
- не параллелит NPC/снаряды/тайлы/жидкости — это гонки данных и вылеты;
- не обещает «+30 FPS кнопкой»: если кадр упирается в GPU, мод его не ускорит, но покажет,
  куда уходит время;
- не трогает ваш мир и сохранения (кроме отложенного автосейва — он просто срабатывает позже).

## Что показывает

Оверлей (по умолчанию **F6**, меняется в Settings → Controls → Keybinds) — аккуратная
панель в левом верхнем углу: крупный FPS, время кадра и две колонки показателей.

- **FPS** — реальная частота отрисованных кадров (число кадров за секунду), рядом
  `frame` — время кадра, `game` — счётчик самой игры `Main.frameRate`;
- `cpu total` и `update / draw` — сколько реально считает процессор в каждой фазе;
- `present / other` — остаток кадра, который не объясняется update+draw (ожидание
  vsync/present, компиляция шейдеров, драйвер). Большое значение = кадр упирается не в CPU;
- `GC / pause`, `alloc` — сборки мусора и аллокации в секунду;
- `spikes 60s` — кадры дольше 25 мс за минуту **без** предзагрузки; `(+N preload)` —
  отдельно те, где предзагрузка была последней миллисекундой, вытолкнувшей кадр за
  vsync (без её среза update+draw уложились бы в бюджет). Если update/draw не влезали
  и без предзагрузки, остаётся их реальная причина (`update`/`draw`/`gpu`);
- `preload`, `autosave`, `section` — прогресс предзагрузки, время последнего автосейва,
  время пересчёта секций в этом кадре;
- `light / tiles`, `walls / bg`, `parallel gore`, `dust / proj / npc`, `proc / threads` —
  подсистемы и загрузка процесса;
- график кадров за последние 120 кадров; белая линия — реальный бюджет кадра,
  который берётся из `Main.frameRate` (при 70 FPS это 14.3 мс, а не 16.7 мс).

## Что сделано против микрофризов

1. **GC в режиме `SustainedLowLatency`** на время игры в мире. Это переводит сборки
   старшего поколения в фоновый режим и убирает длинные «стоп-мир» паузы на
   50–300 мс, которые ощущаются как замирание картинки. Отключается в настройках
   мода (`ReduceGcPauses`).
2. **Предзагрузка секций мира при входе.** Ваниль пересчитывает фреймы тайлов
   (`TileFrame`/`WallFrame`) для секции 200×150 лениво — когда секция впервые
   попадает в миникарту, то есть когда вы идёте в новую сторону. Это и есть рывки
   при движении влево/вправо от уже посещённых мест. Мод сразу после входа
   пересчитывает **все** секции (ближние первыми). Работа идёт не секциями, а
   кусками тайлов с проверкой дедлайна **после каждого тайла** (одиночный `Reframe`
   дерева/самоцвета может стоить миллисекунды). Бюджет адаптивный: `PreloadBudgetMs`
   (по умолчанию 3 мс) — это верхняя граница, а фактический срез = свободная часть
   текущего бюджета кадра минус 1 мс запаса. Поэтому на 70 FPS реально тратится
   обычно 1.5–3 мс, и большинство кадров остаётся в бюджете vsync. Фактическое время
   видно как `preload_ms` в `live.json` / `timeline.csv`; замер v0.8.1: 668 из 672
   секций, 25.2 с чистой работы за 147 с wall time, в среднем 37.8 мс на секцию,
   максимум 126.4 мс. Сверху показывается «Preloading world N%» с ETA. Настройки
   `PreloadWorld` / `PreloadBudgetMs`; в мультиплеере предзагрузка не включается.
   Полностью убрать рывки входа нельзя: загрузка сущностей, первичная карта и
   компиляция шейдеров остаются, а редкие кадры 25–28 мс всё равно случаются, когда
   срез предзагрузки вместе с update+draw чуть не попадает в vsync. Они честно
   классифицируются в `spikes.csv` (`preload`, `gpu`, `update`, `other`) и не
   выдаются все подряд за работу предзагрузки.
3. **Автосейв не срабатывает во время боя с боссом.** Ванильный таймер автосейва
   (раз в 10 минут) продолжает идти, поэтому мир сохраняется сразу после боя, а не
   в середине уворота. Есть предохранитель: если «босс» остался активным навсегда,
   через 10 минут автосейв всё равно сработает. Отключается (`DeferAutosaveDuringBoss`).
4. **Телеметрия пишется в фоновом потоке.** Текст собирается на игровом потоке
   (он читает состояние Terraria), а диск трогает отдельный низкоприоритетный
   поток. Раньше запись `live.json`/CSV могла давать рывок на 5–50 мс, особенно
   когда антивирус сканирует свежие файлы.
5. **Оверлей кешируется.** Строки пересобираются 4 раза в секунду, а не каждый
   кадр: минус сотни аллокаций строк в секунду и лишняя работа GC.
6. **Курсор переехал на аппаратный (v0.6.0).** Старый мод `OptimizedCursor` каждый кадр
   рисовал курсор в маленький render target и сразу читал его обратно **после** всей
   сцены: `Texture2D.GetData` ждал, пока GPU закончит кадр, — по замеру это 38 % времени
   главного потока (9,5 с из 25 с профиля, ~5,4 мс на кадр) и главный источник рывков
   при ходьбе. Теперь это делает сам Engine Optimizer: курсор рисуется в 128×128 target
   **в начале** кадра, когда GPU уже закончил предыдущий, читается сразу; поддержка
   курсора (пересоздание OS-курсора и чтение target) обновляется с частотой 20 Гц,
   а не каждый кадр, и стоит ≈0,4 мс. OS-курсор пересоздаётся только при реальном
   изменении внешнего вида (цвет/масштаб квантуются). Указатель двигает Windows, поэтому он остаётся
   плавным даже когда игра рисует ниже герцовки монитора. Настройка `SmoothHardwareCursor`;
   при любой ошибке мод сам возвращается к ванильному курсору.
7. **Починка профиля управления при входе в мир.** tML добавляет кейбинды модов в профиль
   управления в `PlayerInput.UpdateInput`, но при прямом запуске в мир `DoUpdate` выходит
   раньше, и профиль остаётся ванильным. Моды, читающие свой кейбинд в `OnEnterWorld`
   (так делает Ore Excavator 0.8.9), падали с `KeyNotFoundException` → «Main engine crash».
   Engine Optimizer перед спавном молча добавляет недостающие **пустые** (не назначенные)
   записи — существующие привязки не меняются. Если tML изменит внутренности, шов тихо
   отключается.
8. **`launch-multicore.bat`** — запуск с серверным GC и настройками JIT (см. ниже).

## Курсор и OptimizedCursor

Начиная с **0.6.0** отдельный мод `OptimizedCursor` не нужен: он убран из `enabled.json`
(сам воркшоп-мод можно оставить установленным, он просто не загружается). Engine Optimizer
рисует ванильный курсор — включая смарт-курсор, толстую рамку и `cursorOverride` (курсор
над предметом в чате, кисть и т. п.) — в 128×128 render target в начале кадра и превращает
его в OS-курсор. Клик попадает туда же, куда и раньше: hotspot считается по отступу, с
которым курсор нарисован, поэтому стрелка не «съезжает» относительно точки клика.

Если `OptimizedCursor` когда-нибудь снова включат, два мода начнут бороться за курсор:
оставьте `SmoothHardwareCursor` выключенным (или выключите `OptimizedCursor`).

## Про «использовать все ядра»

Честно, без обещаний: логика Terraria (NPC, снаряды, тайлы, жидкости, физика) —
однопоточная, и мод не может распараллелить её безопасно. Это гонки данных,
рассинхрон мира и вылеты. Полноценный многопоточный движок — это форк
tModLoader, а не мод.

Что мод **реально** распараллеливает (v0.5.0):

- **Gore (кровь/обломки)** — визуальный слой без геймплея. Обновляется на пуле
  потоков через `FastParallel.For`. Модовый gore (`Gore.ModGore`), капли жидкости
  (звук + рябь на воде), особые типы (облака, туман, искры), типы 411–430 и 1218
  (спавнят dust), тип 1208 (спавнит gore и пишет тайлы) и всё, что светится
  (`light > 0`) остаётся на главном потоке. Условие включения: не меньше 128
  активных «безопасных» gore (иначе накладные расходы пула больше выигрыша).
  Настройка `ParallelGore`.
- **Rain (дождь)** — тоже только визуал. Ваниль обновляет капли внутри `DrawRain`
  после отрисовки каждой; мод обновляет их заранее параллельно, а ванильный цикл
  пропускает обновление. Условие: не меньше 400 активных капель (из 750).
  По умолчанию **выключено** (`ParallelRain`): `HighFPSSupport` уже IL-хукает
  `Rain.Update`, `NoxusBoss` хукает `DrawRain`, а выигрыш от переноса работы из
  draw в update почти нулевой. Включать только для эксперимента.
- **Освещение** — ванильный `LightingEngine` уже сам использует `FastParallel`,
  мод его не трогает и не ломает.
- **Server GC** — сборка мусора параллельно, 8 куч на 24 потока (только при запуске
  через `launch-multicore.bat`).
- **Фоновые потоки** — телеметрия, автосейв, загрузка ассетов.

Потокобезопасность: на время параллельной фазы `Main.rand` подменяется на
фасад с генератором на каждый поток, а `Dust.NewDust` и `Lighting.AddLight`
берут общий лок (только пока фаза активна — в обычном коде это один
volatile-read). Если воркер бросит исключение (gore — три подряд, rain — сразу)
или `FastParallel` упрётся в свой 10-секундный watchdog, функция отключается до
следующей загрузки мира, а игра продолжает работать в обычном режиме. Оба хука
можно выключить в настройках мода.

В `live.json` это видно как `upd_gores_ms`, `gore_par_ms`/`gore_par_n`,
`rain_par_ms`/`rain_par_n`, `gore_par_total`/`rain_par_total` и
`parallel_state` (`gore+rain`, `gore`, `rain`, `off`, `failed`).

Ожидания: на обычной игре выигрыш небольшой (десятые доли миллисекунды), на
боссе с кучей gore — заметнее. Основные причины фризов в модпаках всё равно
GC-паузы и однопоточный AI модов, а не gore.

`session.json` показывает `gc_server: true/false`, `cores` и `gc_latency` — так
видно, применился ли многопоточный GC.

### Запуск

Обычный запуск: Steam → tModLoader → Играть.

Многопоточный GC: запустить
`C:\Users\A\Documents\Проект по умолчанию\launch-multicore.bat`
(Steam должен быть открыт). Скрипт выставляет только для этого процесса:

| Переменная | Что делает |
|---|---|
| `DOTNET_gcServer=1` | server GC: сборка мусора параллельно на нескольких ядрах |
| `DOTNET_GCHeapCount=8` | 8 куч вместо 24: меньше резидентной памяти и длинных GC-хвостов, параллельности хватает |
| `DOTNET_gcConcurrent=1` | фоновые сборки |
| `DOTNET_TieredPGO=1` | динамическая оптимизация горячего кода |
| `DOTNET_TC_QuickJitForLoops=0` | методы с циклами сразу компилируются в оптимизированный код — меньше рывков от повторной JIT-компиляции |

Если с server GC стало хуже или закончилась память — играйте через Steam,
мод продолжит работать.

## Диагностика на диске (можно смотреть без скриншотов)

Пока вы играете, мод непрерывно пишет в
`%USERPROFILE%\Documents\My Games\Terraria\tModLoader\EngineOptimizer\`:

| Файл | Что внутри |
|---|---|
| `live.json` | текущий срез, перезаписывается раз в секунду: FPS (`fps_draw` — по числу кадров за секунду, `fps_draw_ema` — сглаженный), frame/update/draw, свет, слои, GC0/GC2/пауза GC, аллокации, загрузка процесса `process_cpu_pct`/`threads`, `section_ms`/`section_n`, `preload_pct`/`preload_ms`/`preload_budget_ms`/`preload_active`, `cursor_ms`/`cursor_state`, `save_ms`/`save_count`, `spikes_last_60s`/`preload_spikes_last_60s`, боссы, биом, позиция игрока, последние спайки (с `preload_ms`) |
| `session.json` | мир, игрок, разрешение, vsync, fixed timestep, освещение, ядра, режим GC, `preload_world`, `preload_budget_ms`, список модов |
| `timeline.csv` | строка раз в 5 секунд: FPS, p95/max кадра, все секции, GC, сущности, `proc_cpu_pct`, число потоков, `section_ms`, процент и фактическое время предзагрузки, биом, координаты, `boss_perf`, `proj_top` (топ типов снарядов, когда их ≥100) |
| `spikes.csv` | каждый кадр дольше 25 мс с полным контекстом: что было на экране, боссы, позиция, скорость, HP, пауза GC, `preload_ms` и **причина** (`cause`: `preload` — срез предзагрузки был последней миллисекундой, вытолкнувшей кадр за бюджет (без него update+draw уложились бы), `save` — автосейв, `gc` — пауза сборщика, `section` — пересчёт секции, `gpu` — кадр не упирался в процессор (ожидание present/GPU), `update`/`draw` — упёрлись в фазу кадра, `other` — явного лидера нет), плюс `unacc_ms` — сколько кадра не объясняется update+draw, и `proj_top` |
| `profile-*.csv` | итоговый отчёт при выходе из мира: avg/p50/p95/p99/max |
| `timeline-*.csv`, `spikes-*.csv` | архивы предыдущих заходов в мир (хранятся последние 8) |

CSV начинаются с полной даты и времени, поэтому записи разных сессий не путаются.
Этого достаточно, чтобы определить, что лагает — без пересылки файлов.

### Если FPS падает ровно вдвое (60 → 30)

Посмотрите на `frame_ms`: если он между бюджетом кадра и двумя бюджетами
(16.7–33.3 мс при 60 FPS, 14.3–28.6 мс при 70 FPS), кадр не успевает в бюджет,
и vsync показывает половину частоты. `vsync` записан в `session.json`. Для проверки
отключите vsync в настройках Terraria и сравните `fps_draw` / `frame_ms` в
`timeline.csv` — обычно просадки «60 → 30» лечатся именно этим.

## Важно

Мод **не** переписывает движок. Terraria — закрытый код, а tModLoader-мод живёт
в том же процессе и может только перехватывать методы через хуки. Полноценная
замена рендера/освещения — это форк уровня `tModLoader` + месяцы работы.

Что ещё можно сделать хуками (следующие этапы):

1. IL-патч отрисовки: пропуск снарядов/dust за пределами экрана (Calamity любит
   плодить тысячи снарядов, которые всё равно рисуются).
2. Кэш статичного тайлового слоя в RenderTarget (камера не двигается — не
   перерисовываем тайлы каждый кадр).
3. Свой проход освещения (GPU-лайтмап) вместо CPU-версии — самый большой выигрыш
   и самый большой риск.

## Настройки мода

Settings → Mod Config → Engine Optimizer:

- `ShowOverlayOnStart` — показывать оверлей сразу;
- `SaveReportOnWorldExit` — писать `profile-*.csv` при выходе из мира;
- `ReduceGcPauses` — GC-режим низких пауз + минимум потоков пула;
- `DeferAutosaveDuringBoss` — не сохранять мир во время боя с боссом;
- `ParallelGore` — параллельное обновление ванильного gore (по умолчанию вкл.);
- `ParallelRain` — параллельное обновление дождя (по умолчанию выкл., экспериментально);
- `PreloadWorld` — пересчитать фреймы всех секций мира при входе (по умолчанию вкл., только одиночная игра);
- `PreloadBudgetMs` — верхняя граница миллисекунд на кадр для предзагрузки (по умолчанию 3). Адаптивный губернатор дополнительно вычитает из бюджета кадра уже потраченное время update+draw и оставляет 1 мс запаса, поэтому фактический срез обычно меньше; `0` — весь мир сразу, окно замрёт на несколько секунд;
- `SmoothHardwareCursor` — свой аппаратный курсор вместо ванильной отрисовки (по умолчанию вкл.). Выключите, если ставите другой курсорный мод: мод вернётся к ванильному курсору, `cursor_state` в `live.json` станет `vanilla`.
- `BossPerfMode` — режим максимального FPS в бою с боссом (по умолчанию вкл.): отключает дым CalamityFables, heat distortion и storm effects, приостанавливает рост травы/лиан, пока босс в радиусе 125 тайлов; после боя возвращает как было.
- `BoostProcessPriority` — приоритет процесса `AboveNormal` на время игры в мире (по умолчанию вкл.): меньше вытеснения игры фоновыми задачами. После выхода из мира возвращается `Normal`.

### Совместимость курсора с модами

Курсор рисуется собственной копией ванильного кода, а не вызовом `Main.DrawCursor`. Это
специально: `Main.DrawCursor` хукают другие моды. Например, аксессуар Calamity с «огненным
курсором» рисует эффект в экранных координатах и перезапускает `SpriteBatch` — внутри
маленького render target это давало чёрный квадрат вместо курсора. Побочный эффект: пока
аппаратный курсор включён, визуальные эффекты модов, которые рисуются хуком
`Main.DrawCursor`, не показываются (как и в OptimizedCursor). Ванильный вид — стрелка,
смарт-курсор, толстая рамка, `cursorOverride`, радужный курсор — воспроизводится точно.

На всякий случай встроена защита: если render target получился почти полностью непрозрачным
(признак чужой отрисовки), мод не создаёт из него курсор, пишет предупреждение в лог и
возвращается к ванильному курсору.

## Сборка

Нужен **.NET 8 SDK** (в комплекте с tModLoader идёт только рантайм).

```powershell
cd EngineOptimizer
dotnet build
```

Готовый `.tmod` автоматически попадает в
`Documents\My Games\Terraria\tModLoader\Mods` и включается в список модов.

Если Steam установлен в другое место:

```powershell
dotnet build -p:TerrariaSteamPath="D:\Steam\steamapps\common\tModLoader\"
```

Или через `build.ps1`.

Проект собран и проверен против tModLoader **1.4.4.9** (хуки `Terraria.On_Main` /
`Terraria.On_Lighting` / `Terraria.On_Gore` / `Terraria.On_Rain` / `Terraria.On_Dust` /
`Terraria.On_WorldGen`, включая `On_Main.Draw`, `On_Main.DrawCursor`,
`On_Main.DrawThickCursor`, `On_Main.DrawInterface_36_Cursor`).
После крупного обновления tModLoader имена хуков могут измениться — тогда правится
один файл `Perf/ProfilerSystem.cs` (курсор — `Perf/SmoothCursorSystem.cs`).

## Структура

```
EngineOptimizer.cs        — точка входа мода
OptimizerConfig.cs        — настройки (клиентские)
Perf/PerfData.cs          — счётчики кадра, секций тика, GC, сущностей
Perf/ProfilerSystem.cs    — хуки движка, GC-режим, отложенный автосейв, оверлей
Perf/SmoothCursorSystem.cs — аппаратный курсор: рисуем в target в начале кадра, кешируем OS-курсор
Perf/KeybindProfileGuard.cs — добавление недостающих записей кейбиндов модов до спавна
Perf/WorldPreloader.cs    — предзагрузка фреймов всех секций мира при входе
Perf/ParallelUpdates.cs   — параллельные gore/rain, thread-local random, лок эффектов
Perf/Telemetry.cs         — live/session/timeline/spikes, ротация архивов
Perf/AsyncFileWriter.cs   — фоновая запись файлов
Perf/PerfLog.cs           — итоговый CSV-отчёт
```
